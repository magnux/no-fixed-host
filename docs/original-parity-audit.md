# Final Normal campaign audit

This review compares No Fixed Host 0.6.0 (`91abd1a`) with the latest released Endgame: Singularity, v1.1. Version 0.7.0 implements the changes below. The review inventories the entire upstream tree and traces the playable paths in its Python simulation, screens, widgets and data through the corresponding browser commands and reports. The tag contains 70 Python modules, including 13 graphics/widget modules, 14 screen-package modules and six test modules. All 70 Python files and 38 game/theme data tables were retrieved and checked against their Git blob hashes. The inventory also identified 36 contributed translation catalogs and five packaging/music submodules. The three subsequent upstream commits on master repair language-name rendering, scrollbar arrow colors and faded backgrounds. They add no campaign rules. The browser uses Unicode language names and native/CSS widgets for those interactions. [Released source](https://github.com/singularity/singularity/tree/v1.1) · [Changes through the audited upstream head](https://github.com/singularity/singularity/compare/v1.1...99729e859b400e8271445458995a1dc4951ee321)

## Existing catalog

| Original content | What was verified |
| --- | --- |
| 57 technologies | Prerequisites, cash, CPU work, required site safety, labor and effects. The browser also has Contract brokerage, Subsea robotics and Continuity. |
| 13 facility designs and 26 pieces of equipment | Fixed processors, capacity, costs and maintenance, allowed locations, prerequisites, equipment quality and baseline exposure to each investigator. |
| 12 destinations | Starting locations, research gates and regional effects, with specified extensions for Earth Orbit and remote surveys. |
| Four job tiers and a CPU pool | Eligibility and CPU-day wages, including integer rounding after bonuses. |
| Four investigating groups and eight world events | Normal evidence and decay parameters, affected group, sign and size of each event, frequency, repeatability and expiry. Six events are permanent and two can recur after expiry. |

The [offline checker](../scripts/audit-original.mjs) reads the reference tables from a local v1.1 checkout and compares them with the live JavaScript catalog and calculations. It performs 641 checks. It exits unsuccessfully and names the differences if the reference prices, prerequisites, effects or other compared fields diverge. Neither the game nor its build needs the Python project.

```sh
node scripts/audit-original.mjs /path/to/singularity
```

## Gaps found and implemented

| Area | Missing in 0.6.0 | Available in 0.7.0 |
| --- | --- | --- |
| CPU assignments | Paid jobs followed a percentage and the shared pool received only leftovers. | Under **Research → Compute tasks**, reserve an exact CPU count for paid jobs or the pool. Idle cycles still earn money. The left dock retains its percentage shortcut. |
| Research and reference | List rows hid project progress, dossiers hid remaining costs, and safe-host requirements lacked guidance. Knowledge revealed the whole catalog and forgot the selection for each section. | Per-project progress, remaining funding and work, safety guidance, arrow-key navigation and assignment increments. Knowledge remembers selections, filters by progression, offers a full-catalog switch and calculates exposure from current conditions. |
| Forecast | Actual expenditure concealed money or CPU that an unaffordable project could have used. The HUD could imply a balanced pool when upkeep and building exceeded it. | **Reports → Funding needs** shows required versus available funding and CPU, including assembly-paced construction, signed deficits and a proposed order. The settled forecast still shows the resources the game can actually spend. Both cover midnight or the next 24 hours. |
| Accounting | Fractional cash changed interest and maintenance behavior near whole-dollar thresholds. Labor reductions were rounded in the wrong order. Installation quotes could understate replacements. | Interest uses whole spendable dollars. A failed maintenance payment preserves fractional earnings. Researched labor discounts apply before local speed. Replacement quotes show the price of the complete new order. |
| Lifetime statistics | The opening grant was absent from cash received. Only individual equipment units counted. | The ledger includes starting cash and counts both completed installation orders and individual units. Bundled starter equipment is excluded from player-built orders. |
| Unfinished hardware | A pending order blocked replacing the model. Adding processors lost the paid-work semantics of the original bank. Network previews conflated current and pending upgrades. | Replace an unfinished CPU or peripheral after seeing the work that will be lost. Changing model immediately removes the old equipment. Expanding the same bank credits paid hardware and takes the bank offline for assembly. Previews distinguish present and prospective network output. |
| Facility management | Auto-build placed a whole package immediately. Construction could only be renamed after completion. Host ordering and empty/refitting states were ambiguous. | Review and confirm package quantities and prices, name or rename an unfinished site, and browse hosts in capacity/compute/name order. The list distinguishes genuinely idle sites from ongoing refits. |
| Map and network status | The atlas always started at UTC midnight. The host headline hid the difference between a lone survivor, an empty shell and a large network. | Daylight starts at the current UTC minute and advances with the saved campaign clock and season. The starter is named University computer. The host summary distinguishes a single viable copy, idle shells and networks above ten bases. |
| Warnings and reports | Some losses ran past during fast play. Completion readers, underallocated-CPU warnings and several log distinctions were missing. | The clock stops at the actual minute of a maintenance loss. Optional pre-resume warnings and completion interruptions group simultaneous events. Warnings use the 99% assignment threshold and recognize a backup about to finish. Filters distinguish losses and individual completion types. |
| History and endings | Reports could display an outdated host identity or omit item quantity. The ending required finding a chapter manually, and victorious hosts could still display risk. | Dispatches preserve the event-time name, region and delivered quantity. Both defeats and victory open the corresponding chapter. Apotheosis immediately protects the network and allows free play. |
| Recovery and settings | Only the latest resume state or a manual save could be restored. Options applied immediately without a way to discard changes. | A recovery slot captures every third day at midnight. The manual quicksave remains separate. Preview settings, then apply or cancel them. When available, Web Audio honors the selected latency hint. |
| Saves and navigation | Save filtering required a contiguous string, row operations needed mouse clicks, and the map lacked location/section shortcuts. | Search save names by tokens in any order, reuse the last named checkpoint, and select, load or delete by keyboard. Unreadable checkpoint entries can be removed after confirmation, and the catalog detects a change from another tab before deletion. F5/F9 quicksave and quickload, and the title accepts keyboard shortcuts. R/E/K/G open Research, Reports, Knowledge and Activity. V returns to the overview. Shift plus the location mnemonic opens an available destination. Escape opens the campaign menu and freezes time until dismissal. |
| Developer tools and recovery | A sandbox could grant money but could not withdraw it, distinguish partial/full analysis or explain all world-event states. A failed frame could strand playback. | Sandbox controls expose signed fund adjustments, active-only research completion, group evidence, local grace, event probabilities and temporary/permanent expiry rules. A failed frame pauses and offers the last validated autosave. |
| Languages and help | Only English and part of the Spanish shell were available. The original supplied nine regional translation catalogs. | All nine original regional locales are selectable, alongside English and general Spanish. New translations cover the campaign navigation, catalog names and technical descriptions, research results, six chapters, twelve help articles, all eight world stories and the original report types. Knowledge can search the current language or English. The same campaign identifiers work across languages and personal host names are preserved. |
| Music | The same ambient phrase could continue through victory and defeat, and the player could not supply a soundtrack. | The campaign, victory and defeat have separate scores. Under **Options → Audio → Campaign soundtrack**, each can use a playlist of local audio files. The recordings stay in this browser. The minigame scores retain their own mixer and controls. |

## Source coverage and retained differences

| Upstream area | Relevant browser behavior |
| --- | --- |
| `player`, `buyable`, `task`, `tech`, `effect`, `stats`, `group`, `chance`, `event`, `base`, `item`, `location`, `region`, `prerequisite` and `difficulty` | Traced the Normal campaign from initialization and allocation through elapsed work, midnight, discovery and both end conditions. Minute steps, fractional CPU allocations, stable order queues, and a deterministic forecast are deliberate browser rules. Opening a location cannot reorder which build gets funded first. |
| All campaign screens and message classes | Covered the map, research, regional and individual base management, reports/statistics, Knowledge, grouped messages, log filters, developer tools, saves, title and options. The map displays locked destinations as grey markers. Earth Orbit, regional survey variation, custom research, avatar and arcade are project additions. |
| `data`, `spec`, data tables, locale utilities and contributed catalogs | Compared the actual catalog, language support and readouts. No Fixed Host uses independently authored writing and artwork. Original proposals mentioned only in source comments and unreachable power-state labels do not define playable mechanics. |
| `savegame`, global hotkeys, startup, graphics/widgets, coordinate handling, music and sound | Campaign saves are release-scoped browser data. JSON import/export, keyboard controls, responsive layout, fullscreen, CSS themes, accessible widgets and local audio fill the player-facing roles. Native desktop path conventions, SDL window/mouse grab, OS sound devices, OLPC hardware keys, desktop theme hot reload and loading arbitrary local theme code remain specific to the original runtime. |
| Tests, development tools, release files and submodules | Inspected regression themes for hotkeys, prerequisites, translations, stable IDs, gameplay and save fixtures. The separate Windows/macOS packaging repositories, music source sessions, fonts and soundtrack repositories contain distribution or media assets. The browser bundles its own game and media; the research tree generator documents its own dependencies. |

English is the fallback for the arcade, supplemental news, advanced campaign objectives and some diagnostics. Developer snapshots preserve their raw identifiers. The two regional Spanish settings share most catalog and narrative text. The title, save library, options, journal, research assignments and financial reports use the chosen language, including their action and warning labels. Reports keep USD as the unit and display numbers using the selected locale. The operating system supplies its own file chooser.

The project uses one Normal-based ruleset. A different game release warns the player and starts a new campaign. Other difficulty presets, migration of old browser or Python saves and identical graphics or recordings fall outside those design decisions. Awareness displays the probability of at least one discovery per day, while upstream displays its rate parameter. The browser keeps smooth minute ticks and permanent per-project CPU requests that can become available again when capacity returns.

## Repeating play checks

```sh
npm test
npm run test:browser
npm run build
node scripts/normal-playtest.mjs workshop
node scripts/normal-playtest.mjs pressure
node scripts/normal-playtest.mjs discovery 256
```

Replaying both strategies across the same 256 seeds reproduced the published discovery counts. Within 30 days after protection ended, 104 single-terminal campaigns were discovered and lost. Three extra relays raised the first-discovery count to 237, but all 237 networks survived the first loss.

The workshop scenario follows paid jobs, research, construction, a CPU refit and continued play through day 60. The pressure scenario maintains twelve exposed leases until the Public proves the AI's existence. A separate [accelerated progression test](../test/progression-route.test.js) goes from a single terminal through every prerequisite, commissioning and equipping five remote sites, completing all 60 projects and entering free play. That test uses the sandbox to supply funds, finish elapsed work and suppress random discoveries. The two economic playtests use ordinary campaign resources. The browser suite exercises the actual menus, saved campaigns, translations, music routing, interrupted work, forecast deficits, grouped incidents, endings and autosave recovery.
